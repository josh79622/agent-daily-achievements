# Decision: the report day runs 07:00 to 07:00, and the schedule lives in launchd

Decided by Josh on 2026-09-21. This supersedes the calendar-day boundary in
`2026-09-17-cross-day-session-window.md`; that decision's rules about session
eligibility and included context still stand, with its day boundaries replaced by
the window defined here.

## Decision

- A report covers `[D 07:00, D+1 07:00)` in the stored report timezone, and is filed
  and shown under date `D`, the starting day.
- The run happens at 07:00 on `D+1` and produces the report for `D`.
- The schedule lives in a macOS `launchd` job, not in a long-running process. Nothing
  has to be left running; macOS runs a missed job when the Mac wakes.
- A wake after several missed days generates only the most recent completed window.
  Older days stay empty and can still be generated by hand from the date picker.
- A day already generated is never generated again by the schedule.

## Rationale

Work after midnight belongs to the night it came from. A 07:00 boundary keeps a late
session in one report instead of splitting it across two dates. Labelling by the
starting day keeps the date picker meaning what it already means, and puts a 1am
session in the report for the evening it continued.

Generating only the most recent window keeps a return from a holiday to one provider
call instead of a burst against Josh's plan limits.

## Consequences

- The collector's day filter, the report file names and the date picker all move from
  midnight boundaries to 07:00 boundaries.
- Reports already on disk (`2026-09-09`, `2026-09-18`, `2026-09-19`) were built on
  midnight boundaries and are left as they are. They are not regenerated.
- "Was this day already generated?" becomes the schedule's idempotency check.
- The 24-hour fallback for a missing system timezone
  (`2026-09-17-local-timezone-scheduling.md`) is unchanged.
